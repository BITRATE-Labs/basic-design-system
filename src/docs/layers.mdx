# Layers

Tooltip, Popover, DropdownMenu and Dialog render their popups in a portal at the end of `<body>`. That lets them leave any container that clips, scrolls or stacks its children. Three rules keep them on top.

## 1. Put `isolate` on the app root

Wrap the whole app in one element with Tailwind's `isolate` class (`isolation: isolate`). The page then forms a single stacking context, so no z-index inside it can rise above the portaled popups, and page code can use z-index freely for its own ordering. This is the setup [Base UI recommends](https://base-ui.com/react/overview/quick-start).

That holds only inside the root. Anything else portaled to `<body>`, such as a toast library, a chat widget or a `createPortal(..., document.body)`, is a sibling of the popups and competes with their `z-50`. Mount it inside the isolated root, or keep its z-index below 50. At 50 or above it covers every shared popup.

## 2. Wrap the app root in `TooltipProvider` once

The stock tooltip expects it, as the [shadcn tooltip docs](https://ui.shadcn.com/docs/components/base/tooltip) say. It groups tooltips, so moving from one trigger to the next opens the next tooltip at once.

```tsx
<body>
  <div className="isolate">
    <TooltipProvider>{children}</TooltipProvider>
  </div>
</body>
```

## 3. Inside a top-layer element, pass `container`

A modal `<dialog>` opened with `showModal()`, and an element with the `popover` attribute shown with `showPopover()`, sit in the browser's top layer, which paints above every z-index. A popup portaled into the body renders behind them. Pass the element to the popup's `container` prop so the popup is portaled into it, and give the element `overflow-visible`. Without it, the dialog clips the popup, and a `popover` element (whose browser style is `overflow: auto`) scrolls to the popup instead of letting it out. If the content must scroll, scroll an inner element.

```tsx
const ref = useRef<HTMLDivElement>(null);

<div ref={ref} popover="manual" className="overflow-visible">
  <Tooltip>
    <TooltipTrigger render={<Button />}>Save</TooltipTrigger>
    <TooltipContent container={ref}>Saves without publishing</TooltipContent>
  </Tooltip>
</div>;
```

`TooltipContent`, `PopoverContent` and `DropdownMenuContent` take `container`. The shared Dialog needs none of this, so prefer it to a native `<dialog>`, which the lint preset reports.

## What the Layering stories check

Each story under **Layering** opens a tooltip or popover and checks with the browser's own hit test that the popup is painted on top and not clipped:

- inside an `overflow: hidden` container, at its edge
- inside a scrolling container, also after it scrolls
- inside a `z-index: 1` stacking context next to a `z-index: 9999` sibling
- inside a `transform`ed ancestor that holds a `contain: paint` box
- inside the shared Dialog
- inside a native modal `<dialog>` with `container`; the `BodyPortal` stories show the popup hidden behind the dialog without it
- inside an element with the `popover` attribute, with `container` and `overflow-visible`
- above an overlay portaled to the body with z-index 49

The `Dialog * Escape` stories open a UI SDK popup (date picker, command palette) inside the shared Dialog and check that one Escape closes only the popup. UI SDK lets the key bubble after closing its popup, and Base UI's Dialog closes on any Escape that reaches it, so each UI SDK wrapper stops the Escape its content used. A new UI SDK popup wrapper needs the same handler and the same story.

Known gap: the token input's `@`/`#` menu keeps focus in the editor and closes from a document listener that runs after the Dialog has already closed, so one Escape closes both. Do not put `TokenInput` inside the shared Dialog. `Dialog Token Input Escape Known Gap` pins this; when it fails, the gap is fixed.
